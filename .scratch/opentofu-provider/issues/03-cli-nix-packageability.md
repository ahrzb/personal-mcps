# Decide how the CLI becomes Nix-packageable

Part of [Map: OpenTofu provider for the hub](../map.md)

Type: grilling
Status: resolved
Blocked by: —

## Question

`packages.pmcp` cannot be written until the repo's packaging story is coherent, and right now
it is not:

- `pnpm-workspace.yaml` has **no `packages:` globs**, and `pnpm-lock.yaml` contains only the
  root importer `.`. So `cli/` is not a workspace member; its dependencies are *mirrored* into
  the root manifest, which is how `pnpm pmcp` works at all.
- `docs/specs/overview/04-tech-stack.md` and `§17` both describe a workspace of `server`, `cli`,
  and `clients/js`. `server/` has no manifest. The spec describes a repo that does not exist.
- The root `package.json` is `private`, has no `bin`, no `engines`, no `packageManager`, and no
  `prepare`. The README's `npm install -g github:ahrzb/personal-mcps` therefore installs nothing
  runnable — a real bug, independent of this effort.
- The published artifact is `@ahrzb/personal-mcp-cli`, built only at `prepublishOnly` by
  `cli/build.mjs`, which type-strips seven files with `module.stripTypeScriptTypes` into
  `dist/*.mjs`. No bundler.

Decide:

1. **Workspace shape.** Make `cli/` (and `clients/js/`, and possibly `server/`) real workspace
   members and regenerate the lockfile, matching what §4 and §17 already claim — or keep the
   root-only lockfile and package `pmcp` from the root importer. The first fixes a documented
   lie and changes every install; the second is cheaper and leaves the lie in place.
2. **Derivation strategy.** `pnpm.fetchDeps` + `pnpmConfigHook` with a pinned `pnpm_10` (the same
   pnpm in all three places: the hook, the fetcher, and the devShell) plus an explicit
   `node cli/build.mjs`. `buildNpmPackage` is wrong here (npm lock semantics) and `node2nix` is
   deprecated. Confirm or overrule.
3. **Runtime.** The CLI's "build" is only type-stripping, so the closure is `nodejs` plus six
   runtime deps (`commander`, `@clack/prompts`, `picocolors`, `wrap-ansi`, `smol-toml`, `yaml`).
   Is a full `stdenv.mkDerivation` warranted, or does a thinner derivation suffice? Note
   `@clack/prompts` is dynamically imported only for TTY prompts.
4. **Version pinning as one source of truth.** Node appears as `>=22.18` in `cli/package.json`,
   as `>=22.18 / 23.6` in `docs/deploy.md`, and as `>=20` in a stale spec line; pnpm is pinned
   only in a CI workflow (`version: 10`); Go is `1.25.0` in `go.mod`; Python is `>=3.12` in
   `pyproject.toml` while the local venv reports 3.14. Does the devShell become the authority,
   and do the manifests then follow it?
5. **Hash maintenance.** `pnpm.fetchDeps` needs a `pnpmDeps` hash that changes with every
   lockfile edit. Who regenerates it, and does CI catch a stale one?

Verification note: the deciding session runs on Windows and cannot evaluate a flake. State how
this decision gets verified (WSL `x86_64-linux`, or `nix flake check` in CI as `gws` does).

## Answer

[§22.7](../../../docs/specs/provider/22-opentofu-provider.md), "This repository".

**(1)** `pnpm-workspace.yaml` gains `packages: [cli, clients/js]`; `server/` gets **no** manifest
because Wrangler builds it from the root, and §4/§17 are corrected to describe the workspace that
exists rather than the one they claim. **(2)** `stdenv.mkDerivation` + `pnpm.fetchDeps` +
`pnpmConfigHook` with one pinned `pnpm_10` shared by fetcher, hook and devShell;
`buildNpmPackage` is wrong (npm lock semantics) and `node2nix` is deprecated. **(3)** Full
derivation rather than a thin wrapper, installing `dist`, the pruned store and a `bin/pmcp`
wrapper. **(4)** The devShell is the version authority — `nodejs_24`, `pnpm_10`, `go_1_25`, `uv`
— and the manifests follow it: `cli/package.json`'s `engines`, `docs/deploy.md`'s prose and the
stale `>=20` spec line are all corrected **to** the devShell. It sits beside `pnpm install`
rather than replacing it. **(5)** `pnpmDeps` is regenerated by whoever changes a dependency, and
`nix flake check` in CI is the mechanism that catches a stale hash.

The decision the ticket really existed for, which earlier drafts walked past: **the root manifest
loses its six mirrored CLI dependencies.** Keeping them means two manifests with independently
drifting ranges, where npm and Nix resolve from `cli/` while every local `pnpm pmcp` resolves
from root. After the workspace change pnpm gives `cli/` its own `node_modules` and `pnpm pmcp`
resolves upward into it. The closure is **five** packages, not six, once ticket 06 lands —
`yaml` is imported only at `main.ts:29`, by the planner.

Also fixed in passing: the README's `npm install -g github:ahrzb/personal-mcps` is removed. The
root is `private` with no `bin` and no `prepare`, so it installs nothing runnable today.

Verification, given development happens on Windows: `nix flake check` and
`nix run .#pmcp -- --version` under WSL and again in CI. `pnpm install && pnpm pmcp --version`
verifies the workspace change only and does not substitute.
