Board notes
• The record is a request inspector. Head: the outcome swatch, the title, the time, Close. Body: Search this record…, the Record field table (when, principal, event, app, tool, outcome with its raw code, duration, client, session, id — every id a button that filters by it and closes the drawer), then Arguments / Result / Detail as collapsible JSON trees with the first level open.
• Stubs and redactions are shown as what they are, and the two stubs are not the same thing: content holds one ‘blob image/png · 4.2 MB’ per unstructured block, while a body past AUDIT_BODY_CAP_BYTES replaces its whole column with a single ‘oversize · 20 KB’ (§15) — sizes per §13’s KB/MB rule. ‘redacted’ draws as a stub chip: a masked leaf is never an empty string.
• The three no-bodies sentences are §13’s, verbatim, and the refusal one wins first: several refusals happen before any redaction map exists, so no setting could have made bodies appear.
• The chain timeline is the ledger’s own join. detail.approvalId now rides the four approval.* rows, the tools/call refused −32003, and the tools/call dispatched after the claim (brief §1) — which is the whole of what makes “asked → you approved → ran” drawable. It reads in WRITE order, ts then id: approvals.check records the request before the gateway records the refusal it threw, so the request always takes the lower id.
• Bodies arrive on their own. The window read is slim (no args_json / result_json — projected away in SQL, never parsed to be thrown away); the drawer fetches GET /api/hub/audit/:id when it opens, so a record id outside the loaded rows still opens.
• A code never stands alone (owner, 2026-09-21: “I literally won’t know what −32001 is, it’s not like 404”). Every outcome has a label in the hub’s own §7 words, and the four refusals and error have a sentence — both live once, in derive.ts. The record’s outcome row reads chip · label · dim raw code (denied · not permitted · -32001) with the sentence beneath; the legend drops the codes for words; a waterfall line reads the label plus its failureClass, never class · code. Row chips and the facet rail keep the short class names. The raw code is printed in exactly one place, the record — because that is the value pmcp audit --outcome and the export take.
• No reason is invented. A −32001 carries no detail at all — §7 keeps its three sources indistinguishable — so the record shows the class, the raw code, and nothing it does not have. A −32000 carries detail.failureClass (plus upstreamStatus where an upstream answered one), which is what lets an owner tell a down upstream from a timed-out tunnel.
