Board notes
• Path from a click. Each rendered key carries its dotted path; an array index is dropped on the way (items.3.token → items.token), which is what the masker already does — a path meeting an array applies to every element.
• One op, no new op. The popover posts app_update with redact or redact_results equal to the current map plus one literal-keyed entry per checked tool (or minus one, for Remove). The route reads the map, merges, writes — the same merge the Recording pane does.
• Named tools, never “every”. The “also takes this path” list is the catalog walked for the clicked path: each tool’s input schema, $refs resolved the way the writeOnly walk resolves them. Only tools that carry the path are offered, pre-checked, as one collapsed group row at any length — one popover shape, no threshold. Limits, shown not hidden: a result key on a proxied app offers this tool only (no cached output schema to walk); a schema-unsound tool is listed as “unknown” and unchecked.
• Forward-only, stated. Scrubbing recorded rows would rewrite audit and approval bodies: a new op, a CLI command, and a claim the record of record has been edited. Left out; the badge in panel 4 keeps the exposure visible instead.
• /audit gains one mutation. It has none today (§13: no CSRF surface). The popover’s form carries the token and a return target; the alternative is a link into the Recording pane prefilled, which is also the scripting-off path — every key is that link, and the popover intercepts the click when script is on.
• Both directions. Keys under Arguments write to redact; keys under structuredContent write to redact_results. Keys inside stubbed content blocks do not exist — blocks are never stored.
• Recording pane shrinks. With this in place the pane’s editor is a list with Remove and one Add row; adding from evidence is the primary path. The Add row stays for the proxied case, where nothing is recorded to click on until you have masked what you already know is secret.
