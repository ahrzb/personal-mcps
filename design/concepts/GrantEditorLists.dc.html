Board notes — what this costs the data model
• One extension: a grant entry is a role name or <family>/<pattern> with family in tools, prompts, resources. Same pattern grammar as roles (anchored regex, literal fast path, * aliases .*; resource patterns match the URI). Validation: family known, pattern compiles, the same two length caps. No declaration needed, so the undeclared-role warning and the proxied hard error do not apply to inline entries.
• The gate changes one line: the per-family union takes an inline entry as one pattern in its family. all, allow-wins, approval, reach on every page — unchanged, because they all consume the union.
• Wire, provider, CLI: nothing new in shape. pmcp_grant already carries allow and approval as sets and pmcp grant set already takes --allow / --approval (§22); an inline entry is one more string in those sets. grant_set and agent_list keep the role[:approval] strings as the wire encoding, with family/pattern allowed where a role name was. The YAML file is retired with the planner (§22), so it gets no spelling.
• Add… is a picker, not a text box. It opens a searchable palette over the catalog and the roles the page already holds (the same reads the reach card needs), so no request is made while typing. Rows show where each item already stands so the owner is not guessing; adding keeps the palette open for the next one. Without script the input is a native <datalist> and Add is a submit.
• Versus the per-role editor: that one can only choose among the app’s roles; this one can also name a single item, which is the difference the owner asked for. Both compute the same effective access; if this one is chosen, the per-role board is retired.
