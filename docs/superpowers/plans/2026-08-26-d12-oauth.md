# D12 — Inbound OAuth: the hub as an authorization server

> Spec: **§19** (whole section), plus the amendments it made to §2 (the `.well-known`
> segment), §4 (the two new plugins), §5 (pointer), §7 step 1 (the OAuth credential leg
> and the challenge), §8 (`connection_list` / `connection_revoke`, the parity
> exception), §13 (`/oauth/consent`, `/oauth/connections`), §14, and §18 decisions 1,
> 13, 23, 24, 25.
>
> **Runs first.** D13 (§20) consumes nothing from this dispatch, but both touch
> `gateway.ts`/`index.ts`, and the one-mutating-dispatch rule of the orchestration plan
> makes them serial. OAuth first because it is the feature the owner is blocked on: a
> claude.ai connector cannot attach to this hub at all today.
>
> **Precondition: D11 is gated.** §19.7's invariant is stated against D11's
> credential-family gate, which is mid-edit in `identity.ts`/`web.ts` as this is written
> — see `docs/superpowers/plans/2026-08-26-d11-remediation.md`. This plan deliberately
> names no line numbers in those files. The shape §19.7 relies on is that plan's PSD
> follow-up: the gate is a fail-closed **allowlist** (an `Authorization` header is
> admitted under `/api/auth` only at `/sign-out` and `/device/*`), which is what makes
> `/api/auth/token` — mounted by `jwt()`, converting a session into a hub-signed JWT —
> unreachable with a bearer without anyone having to remember it exists. If D11 lands a
> deny-list instead, §19.7 is false and this dispatch does not start.

## Grain and dispatch shape

**Grain:** one workflow, Opus for the oracle-authoring and the door leg, Sonnet for the
mechanical spread (pages, ops table rows, CLI rows). Standard gate per the orchestration
plan, including the standing deploy + live smoke step.

**Shape:** probe FIRST, as D4 did — the toolchain is contested in exactly one place and
a red probe is a spec escalation, not an execution failure. Then oracles → 2 adversarial
verifiers → reconcile → implement in dependency order → verbatim check → PSD → fix.

**Probe stage (blocking, ~1 agent).** Seven observations, none reasoned. Each is a
sentence §19 states as fact about a package this repo has not installed yet; the first
draft of §19 asserted one of them wrongly (the verify API), which is why the bar here is
"observed", not "read in a changelog":
1. `pnpm add @better-auth/oauth-provider@1.7.1` resolves against the pinned
   `better-auth@1.7.1` and `better-call@1.4.0` with no peer conflict.
2. `(await auth().$context).baseURL` printed once from inside workerd — everything about
   the well-known paths and the metadata document's endpoints depends on it being
   `PUBLIC_ORIGIN + /api/auth`.
3. The jwt plugin's **default EdDSA/Ed25519 key generation and signing on workerd**. If
   workerd's WebCrypto does not satisfy `jose` here, `jwks.keyPairConfig.alg` moves to
   ES256 — a one-line config change, but one that must be known before the migration is
   generated (the `jwks` row carries `alg`).
4. **The verify-side API's actual name and shape** (§19.1). `verifyAccessTokenRequest` /
   `verifyJwsAccessToken` do **not** exist in the installed tree; what exists is
   `verifyJWT` from `better-auth/plugins/jwt` (payload-or-`null`, reads `jwks` through the
   auth adapter, resolves its auth context from AsyncLocalStorage) and `jose` as a
   transitive dependency. Observe whether `verifyJWT` can be driven from a Hono handler at
   all, and what one call costs in D1 reads. The answer picks the door's verify path
   between `verifyJWT` and `jose` + `createRemoteJWKSet`; both satisfy §19.6, so this is
   the last thing blocking group C rather than a spec question.
5. **The signed-`oauth_query` consent contract** (§19.5 step 2). Watch `/oauth2/authorize`
   actually sign the query, `/oauth2/public-client-prelogin` actually accept it, and
   `/oauth2/consent` actually take `{accept, oauth_query}` with a session cookie. §19.5's
   "the page cannot invent, drop or edit a parameter" is the entire reason the consent
   screen is not a place authority can be widened; if the query is unsigned, the design
   changes rather than the page.
6. **Server-assigned `client_id`** (§19.3). POST a DCR body carrying its own `client_id`
   and confirm a *different* id comes back. If a client can choose its id, §19.4's
   `UNIQUE (owner_id, client_id)` becomes an impersonation primitive and the hub must
   assign ids itself before anything else ships.
7. **Exact-string redirect-URI matching** (§19.3). Register a client, then attempt
   `authorize` with the same URI differing by a trailing slash, an added port, and an
   added path segment; each must be refused **before** any consent screen renders, and the
   registered string must be accepted. The hub performs the final browser redirect (§19.5
   step 4), so loose matching here is an open redirector carrying an authorization code —
   if the provider matches loosely for any shape, the hub validates before redirecting.

**Probe outcome (2026-08-26 — overall AMBER, ran; the dep is installed).** Six GREEN, one
AMBER, no RED. Obs 1/2/3/5/6/7 are exactly as §19 assumes. The AMBER is obs 4 and it
forced one spec edit, already made in §19.1:

- **Obs 4 (verify API) — §19.1 corrected.** The door's primitive is
  `verifyJwsAccessToken` from `better-auth/oauth2` (re-exported from

  writes it on provisioning and back-fills it in 0005, as §19.3 pins — the "row could be
  dropped" branch is closed.
- **Open question 5 — RESOLVED.** Ed25519/EdDSA key-gen + sign works on workerd; `jwks`
  carries `alg=EdDSA`, `crv=Ed25519`. No move to ES256.
- **§19.4 confirmed:** D1/workerd blocks better-auth's auto-migration (`SQLITE_AUTH` on
  introspection). 0005 is generated **offline** with `@better-auth/cli generate` and
  checked in, exactly as §19.4 mandates. `getAuthTables` confirmed the eight

## Exit criteria

**Mechanical:** the six suites below green; `node scripts/test-inventory.mjs` shows
only `todo → passed` for this dispatch's cases; `npx tsc --noEmit` exit 0; `wrangler d1
migrations apply` clean on a fresh DB **and** re-applying is a no-op; deploy + `pnpm
smoke` against the deployed origin passes including the new OAuth walk.

**Judged:** the PSD stage judges `oauth.ts` as a module — what does it hide? (The right
answer is "that better-auth is the authorization server at all": the door leg should ask
`oauth.ts` for a principal, not for a token payload.) And two adversarial reads: the
consent page against §19.5 — can any request parameter be edited between the redirect and
the POST? — and the door leg against §19.6 step 3, with one question, traced by hand
through the code rather than argued: **is there any input at all for which a JWT-shaped
bearer reaches the session lookup?** The leg is terminal or this section is a privilege
escalation, and "we return early on every branch we thought of" is not the same claim.

### `scripts/smoke.ts` (live, against the deployed worker — no browser, no claude.ai)

The walk, as one smoke step that fails the deploy gate if any leg fails: register a
client at `/oauth2/register` → GET `/.well-known/oauth-protected-resource/<user>/mcp` and
`/.well-known/oauth-authorization-server` → `authorize` with PKCE + `resource` → follow
to `/login`, sign in as the bootstrap user → follow to `/oauth/consent`, read the CSRF
token, POST accept with a service account the smoke created → capture the code from the
redirect → POST `/oauth2/token` with the verifier and `resource` → assert the access
token is a JWT whose `aud` is the namespace's canonical aggregated URL → call `tools/list`
and `tools/call` on `/<user>/mcp` with it, **and one scoped call on `/<user>/mcp/<slug>`
with the same token** (the audience is namespace-wide, §19.6 — if that leg 401s, the
audience rule regressed) → `audit_query` shows the calls under `sa:<slug>` → revoke the
connection → the next call gets 401 with the challenge → cleanup. The walk sends no
`Authorization` header on any `/api/auth` request: if it needs one, §19.7's allowlist
argument is wrong and the gate has to be revisited before this ships.

- `SMOKE · §19 · the full OAuth round-trip mints a JWT that reaches tools/call as sa:<slug> on both endpoint shapes, and revoking it stops the next call`
