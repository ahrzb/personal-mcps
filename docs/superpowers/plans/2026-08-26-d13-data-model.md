## Grain and dispatch shape

**Grain:** one workflow. Opus for the pure-core widening (`registry.ts` — the pattern
language gains a family dimension, and that is the subtlest code in the repo after the
`writeOnly` walk) and for the DO (`tunnel.ts` — catalog keys and the capability warm are
hibernation-adjacent). Sonnet for the door routing, the CLI rows, and the client-library
pass-throughs. Standard gate, including the standing deploy + live smoke step.

**Shape:** no probe — nothing here is a contested toolchain; every method rides the
envelope `tools/call` already uses. Oracles → 2 adversarial verifiers → reconcile →
implement in dependency order → verbatim check → PSD → fix. The PSD stage judges one
question above all: after this dispatch, is `ServiceBackend` still one seam, or has it
become four parallel ones?

## Exit criteria

**Mechanical:** the suites below green; inventory diff shows only `todo → passed` for
this dispatch; `npx tsc --noEmit` exit 0; `uv run pytest` green; `pnpm contracts:update`
regenerates `contracts/tunnel-frames.json` **and `contracts/initialize.json`**, and the
byte-diff against the committed copies is exactly the roles-shape addition and the
`prompts` capability — nothing else moves in either fixture, and in particular the
aggregated `initialize` answer stays one static result; deploy + `pnpm smoke` green.

**Judged:** the PSD question above, plus one adversarial read of §20.2 against the
implementation: is there any path on which a resource URI leaves the aggregated
endpoint?

## Open questions recorded (not resolved by this plan)

1. Whether the hub should ever compose `ttlMs` as `min(service ttlMs)` across a fan-out
   instead of minting its own constant. §20.5 keeps the constant and records the gap.
2. Pagination: the hub sends no `cursor` and reads no `nextCursor`, so a paginating
   service is silently truncated to page one — already true for `tools/list`, unmeasured
   because no in-tree service paginates. Fixing it means a hub cursor that encodes a
   per-service cursor vector.
3. Whether Claude Code surfaces `resources/templates/list` at all (its docs describe
   @-mention resources but never name templates).
4. Whether hosted claude.ai connectors consume elicitation. Its "not yet supported" list
   names resource subscriptions and sampling but is silent on elicitation; Claude Code
   definitely supports it.
5. Whether the hosted connector surface speaks 2026-07-28 at all, or is still an
   `initialize`-era client. It does not change any decision here — the initialize shim
   (§7) already covers it — but it decides whether prompts reach that surface today.
6. Workers billing and DO hibernation behavior for a long-lived SSE response, and
   whether a DO can hand a `ReadableStream` across an RPC boundary without pinning
   itself awake. Both are load-bearing for any future `subscriptions/listen` and neither
   is answerable from this repo — a Cloudflare-docs pass or a spike, if push is ever
   wanted.
