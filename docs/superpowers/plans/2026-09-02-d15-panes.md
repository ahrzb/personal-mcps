## Implementation constraints (violating any one makes oracle rows unassertable or vacuous)

1. **The gate is a prefix rule, not a per-route call.** One group for `/settings/*` proves
   cookie + recent auth + no bearer before any pane or POST runs — the two ops-backed panes
   included, which is *stricter* than `/oauth/connections` was (§13 accepts this).
2. **Markers come from the pane calls.** One settings loader reads `/get-session`,
   `/list-sessions`, `/passkey/list-user-passkeys`, `token_list`, `connection_list` once
   per render and hands both the rail and the active pane their numbers; a rail count is
   the length of the list its pane renders — asserted, not assumed.
3. **One URL per pane.** `/settings` renders Password; `/settings/password` is a 404.
   `/apps/<slug>` renders Tools; `/apps/<slug>/tools` is a 404. No redirect aliases.
4. **Mutations belong to a pane.** Every redirect-back (`?done=` / `?failed=`) and every
   `?confirm=` rides the owning pane's URL — `paths.settingsConfirm` takes the pane.
5. **`/oauth/connections`**: GET answers `301` to `/settings/clients`; the POST dispatcher
   is `/settings/clients/:op` and nothing posts to the old path.
6. **Password**: `PASSWORD_MIN_LENGTH` is one exported constant (identity → better-auth
   option → the rendered hint); the hub pre-checks only new ≠ confirm; better-auth's error
   *codes* (`INVALID_PASSWORD`, `PASSWORD_TOO_SHORT`) select the field; the translation
   forwards better-auth's `Set-Cookie` exactly as sign-in does; `N` is `/list-sessions`
   length minus one, read before the call.
7. **`/apps/<slug>` reads through the door's seams**: the listing is `listScoped` under
   the owner principal (unfiltered by §7 step 2 — not a copy of it), reachability is
   `registry.matchesPattern` over `agent_list`'s grants and the app's roles (per family:
   tool names, prompt names, resource URIs / raw `uriTemplate`), the pure computations
   live in a Node-clean module with unit rows.
8. **Reserved static segments are derived** from the `/apps/` route table the way
   `RESERVED_ROUTES` is derived, and `app_create` refuses them with the same error shape
   as `pmcp`; `routes.test.ts` walks them.
9. **Dimming reads the capability set** (tunnel: registration-time; proxy: declared
   `capabilities`, absent ≡ `[tools]`); a failed proxied live listing renders **blank**
   markers, never `—`.
10. **Existing rows that pin the old world are deleted-and-replaced, never left red:**
    `web-pages.test.ts` 18 (`/settings` renders no ops-backed form — now true of the
    Sign-in group and Sessions only), 25 / 25a / 26 / 27 (re-pointed to pane URLs), the
    §13/§19 `/oauth/connections` row at :1481 (becomes the clients-pane row);
    `routes.test.ts` 1–2 must still hold with the new segments (derived, so no edit —
    verify). `PagePropsByName.agent` is a rename leftover and becomes `settings`.
11. **Tunneled catalogs in the worker project are planted by registering a `FakeApp`**
    (`hygiene.test.ts` and `order.table.test.ts` already do); proxied listings come from
    `fake-upstream`. A "tools declared / not declared" pair is what makes the dimming rows
    non-vacuous.
12. **Passkey ceremonies cannot run in-process.** Rows pin what the page *emits* (the
    script, the endpoints it names, the base64url contract) and the stamp through a seeded
    row; the ceremony itself is a gate leg in a real browser.
13. **The states preview is a kept reference, not scaffolding.** `server/dev/preview.ts`
    + `fixtures.ts` (`wrangler dev -c wrangler.preview.jsonc`, launch name `preview`) stay
    for good as the demo of every screen and component state — the owner reads it beside
    the boards. Its header no longer calls itself throwaway; `PagePropsByName` keeps every
    page (and every pane of a paned page) enumerated so a page without a fixture is a
    type error; each state a board draws (empty, populated, each refusal, each success
    notice, each confirm dialog, archived, unreachable, dimmed) is one named fixture; the
    gate opens the index in the Browser pane and walks the new entries.

### Constraints the oracle rows add (2026-09-02 — seams, exported names, helpers)

Numbered separately from the thirteen above: the rows say "plan constraint n" for the list above and "constraint n" / "[n]" for this one.

1. `paths` gains the five non-landing settings pane URLs as PLAIN STRING VALUES beside `paths.settings` — `settingsTwoFactor: "/settings/two-factor"`, `settingsPasskeys: "/settings/passkeys"`, `settingsSessions: "/settings/sessions"`, `settingsTokens: "/settings/tokens"`, `settingsClients: "/settings/clients"` — never a nested object or a function, because `routes.test.ts`'s `candidateSegments()` and every walk here read `Object.values(paths)` filtered to `typeof value === "string"`. `paths.oauthConnections` STAYS as a value (it is the 301's source URL); nothing renders a link to it.

2. `paths` gains the app-page builders and every link, form action and row builds from them: `paths.appDetail(slug)` → `/apps/<slug>` (Tools, the landing pane), `paths.appPane(slug, pane)` for the seven non-landing panes (`prompts|resources|roles|overview|access|token|danger`) — no `tools` member, since a `paths` entry for the landing alias would be a spelling of a 404. **Group A owns `paths.appDetail`, not group C**: C and D are declared concurrent in separate worktrees and D's bound-to-link row imports it, so C's ownership would block D from compiling.

3. `paths.settingsConfirm(pane, kind, id?)` and `paths.appConfirm(slug, pane, kind, id?)` take the OWNING PANE first and return that pane's URL carrying `?confirm=<kind>[&id=<id>]` (plan constraint 4); every caller moves with them and nothing hand-builds a confirm URL. `SettingsConfirm` gains `{kind: "revoke-connection"; id; client}` (the shape its `revoke-session` member already has) and a `{kind: "revoke-other-sessions"}` member with NO id, and `model.ts`'s `settingsConfirm` reader must accept the latter or the Revoke-all-others journey has no dialog to open. `revokeLinkFor` moves with the new signature to the Sessions pane's URL — it is the seam the Revoke row walks.

4. Pane POST targets keep the final-segment convention under the OWNING pane's prefix: `paths.tokenRevoke(id)` = `/settings/tokens/token_revoke?id=…`, `paths.connectionRevoke(id)` = `/settings/clients/connection_revoke?id=…`, `paths.appOp(slug, op, args?)` = `/apps/<slug>/<op>?…`, with every non-control argument on the query string under the op's own field name. Redirect-back is `303` to the owning pane's URL with `?done=<op>` / `?failed=<op>&reason=…` — `web.ts`'s existing `noticeUrl(back, op, outcome)` with `back` the pane, so only the destination is new.

5. TWO exceptions to that redirect, both because a plaintext key must never ride a URL (§15): the Token pane's **Issue new token** and `paths.appCreate` answer **200 with the once-only reveal rendered in place**. `dispatch()` unconditionally redirects `303`, so Issue is a route of its own; its target still keeps the final-segment convention so parity direction B can describe it.

6. THE SEAM EVERY RAIL ROW RESTS ON: each paned page renders exactly TWO pane navigations, each a `<nav>` with its own pinned `aria-label` — the rail and the mobile pill row — and the test helper is `railEntries(html, navLabel)`, which narrows to that nav before walking its anchors and returns `{href, label, marker, current}` (`marker` is `""` when the entry has none). Proposed labels, pinned as verbatim strings: `"Settings panes"` / `"Settings panes, compact"` and an equivalent pair for `/apps/<slug>`. Without it the rows are RED, not merely weak: `layout.tsx:85-92` already renders `<a href="/settings" aria-current="page">` into every signed-in page, and the pill row repeats all six hrefs markerless (`Number("")` is 0, not NaN). Two `<nav>`s on one page need distinguishing accessible names anyway, so this is an accessibility contract, not a class name.

7. Every rail entry is exactly one `<a href="<that pane's paths URL>">` containing a label element and, when the pane has a marker, a trailing marker element, so the walk reads no class. THE ACTIVE ENTRY IS STILL AN ANCHOR — `design/Settings.dc.html:52` draws the active Password entry as a `<div>`, against which the rail walk sees five entries where §13's table names six. The two settings group headings render the literal text `Sign-in` and `Access`, the app page's `App` and `Access` with the Danger zone ungrouped after them. Password, Overview and Danger zone render NO marker (their table cells read `none` unbackticked); the Roles pane's `none` is a literal marker string and is different.

8. The Two-factor rail marker carries a TEXT-ACCESSIBLE state (an `aria-label`, `title` or visually-hidden span) that differs between enabled and not-enabled and is never numeric. `design/Settings.dc.html:55` draws a bare coloured `<span>` with no text and no accessible name; against that markup the only observable difference is `background: #15803d` vs the off colour, which §7 puts squarely on the incidental side. Land it as what it is — an accessibility floor a status marker owes anyway, which happens to make the marker assertable — and flag it for the owner rather than presenting it as a spec consequence.

9. Every POST the settings panes render lives under the `/settings/` prefix and every credential target is declared on `paths.auth` — `changePassword: "/settings/change-password"`, `revokeOtherSessions: "/settings/revoke-other-sessions"` included — because `BETTER_AUTH_ACTIONS` (final segments of `paths.auth`) and `SETTINGS_CREDENTIAL_TARGETS` (`paths.auth` values under the `/settings/` prefix) are both DERIVED from it; a credential target declared anywhere else makes the row-18 replacement and the prefix-gate row fail for the wrong reason. The two op dispatchers become `/settings/tokens/:op` and `/settings/clients/:op`, and `app.post("/oauth/connections/:op")` is removed from `web.ts`.

10. `credential()` in `web.ts` must take the OWNING PANE as a parameter: it currently hard-wires `noticeUrl(paths.settings, op, …)`, so every credential POST redirects to the root no matter which pane drew the form (`dispatch(back)` already takes it). Without this seam the redirect-back row is red regardless of what the panes render. Its refusal mapping is by better-auth's error CODE (`INVALID_PASSWORD`, `PASSWORD_TOO_SHORT`), which means `refusalOf` — today reading only the body's `message` — must read `code` for this route.

11. `PASSWORD_MIN_LENGTH` is exported from `server/src/identity.ts`, is what `emailAndPassword.minPasswordLength` is set to (today `identity.ts` sets neither, so better-auth's default 8 stands), and is the ONLY source of the rendered hint's number. Its VALUE is **12** (§4/§13, against better-auth's default of 8) — no row asserts the literal, per §7's "if the assertion names a number … put it behind a named constant"; the constant IS the named thing and its value is the implementer's to land. `maxPasswordLength`'s default of 128 stands and is likewise unasserted.

12. The Password pane's rendered control names, because every row types into controls the page drew (`typedInto` fails otherwise): `currentPassword`, `newPassword`, `confirmPassword`, and the checkbox `revokeOtherSessions` rendered `checked`. The first, second and fourth are better-auth's own body keys (verified in better-auth@1.7.1 `dist/api/routes/update-user.mjs`); `confirmPassword` has no better-auth counterpart and is named here so the walk is not respelling it. `N` rides the success redirect, counted from `/list-sessions` immediately before the call, because after `revokeOtherSessions` the posting cookie is dead and the pane re-renders under the fresh one.

13. THE `/settings/*` PREFIX GATE NEVER READS `Authorization` — this is the existing `requireOwnerSession` contract ("Cookie ONLY … an Authorization header on a web route is not a credential here"), kept, not changed: a bearer with no cookie is the login redirect (302) on every pane and every POST, a device-flow token replayed as a cookie resolves to nobody, and a valid cookie with a stray header beside it proceeds. No row pins a 403 under `/settings/` — §13's "no-bearer" is the structural rule above, and the 403 a bearer earns is the auth mount's `BEARER_ADMITTED` guard at `/api/auth/*` (the auth-matrix row). The reconciler's draft asked for a new 403-on-header rule here; it was an invention beyond §13 and is withdrawn. Corollary that stands: `mutation` resolves the session BEFORE `checkCsrf`, and `checkCsrf` answers its own 403, so any bearer row must carry the page's real CSRF token or its refusal proves nothing about the gate.

14. DIALOG-ONLY FORMS ARE THE RULE, NOT THE EXCEPTION, and every walk over the panes must render the `?confirm=` URLs as well as the bare panes. `settings.tsx` renders `ConfirmDialog` as `{confirm ? … : null}` and `apps.tsx` does the same, so Disable two-factor, Remove passkey, Revoke session, the clients pane's Revoke and both danger-zone controls exist as forms ONLY under the query. (§13 does not put the Tokens pane's Revoke/Remove behind a dialog, so those are found inline — do not "fix" the walks into dialogs-only.)

15. Case 24 already orders `sign-out` last for exactly this reason; the same sort key covers both. Where a walk needs a stale and a fresh session for one owner, seed them in separate namespaces so the new target cannot spend the other's.
